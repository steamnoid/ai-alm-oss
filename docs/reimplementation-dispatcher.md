# Re-implementation notes — dispatcher

Kruczki z live implementacji `aialm-oss-dispatcher` (banalny pool, skill robi całą Jirę).

- **Banalny dispatcher — zero mutacji Jiry w dispatcherze.** Dispatcher nie dotyka `AIALM STAGE/ROLE/AGENT` ani `transitionIssue`. Jedynie: scan `status="AWAITS AGENT PICKUP"` (JQL `project = <KEY> AND status = "AWAITS AGENT PICKUP"` via `JiraClient.searchJql`) → odczyt `AIALM AGENT` (CID) per ticket (wartość = nazwa skilla `aialm-oss-*`) → `docker run -d` per ticket `npx opencode run <agent> <key>` (via `buildDockerRunSpec`). Skill w kontenerze robi **całą** interakcję: początek → `IN_PROGRESS_BY_AGENT/AGENT WORKING`, treść (proposals/summary), koniec → `AWAITING_HUMAN_APPROVAL/AWAITS HUMAN APPROVAL` (per AGENTS.md exclusive mutator; skill jest jedynym mutatorem treści). To minimalizuje coupling i zachowuje one-shot/no-daemon kontrakt orchestratora. Live verify na `WELLBEINGT-5`: pickup `AWAITING_AGENT_PICKUP/PO?/aialm-oss-po-analyze` → start `IN_PROGRESS_BY_AGENT/PO/aialm-oss-po-analyze` + native `AWAITS AGENT PICKUP->AGENT WORKING` (`transition_id 3`), koniec `AWAITING_HUMAN_APPROVAL/PO/none` + `AGENT WORKING->AWAITS HUMAN APPROVAL` (`id 4`).
- **Routing 1:1 — AGENT to skill.** `agentToSkill` = identity; `isDispatchableAgent` = `aialm-oss-*` prefix, `none` → skip. Przy `AWAITING_AGENT_PICKUP` AGENT jest już wypełniony przez orchestrator (konwencja pickup), więc dispatcher nie decyduje o skillu — tylko go uruchamia. Ignoruj tickety bez dispatchable agenta.
- **Scan (`scanPickupTickets`, `dispatcher/index.ts`).** `searchJql(pickupJql(project), [cids.stage, cids.agent, 'status'], limit)` → map przez `fieldValue` (`{value}` shape vs string) + filtr `agent !== 'none'`. `pickupJql` order `updated ASC` dla deterministycznego FIFO. Pure + testowane seam-em `makeJira` (jak `orchestrate.test.ts`).
- **Docker (`buildDockerRunSpec`).** `docker run -d --name aialm-<proj>-<key>-<ent> --label aialm.dispatch=<key> --label aialm.project --label aialm.skill` + deterministyczny `HEALTHCHECK` (`--health-cmd 'cat /proc/*/cmdline | tr "\\0" " " | grep -q "opencode" || exit 1'` — via `/proc`, nie `ps`, bo `procps` nie w każdym base), interval 15s, timeout 5s, retries 3, start-period 10s — health to **monitoring tylko** kontenera; reconcile Jiry robi skill. Mounty: `$(pwd):/app` (`-w /app`), `--env-file $(pwd)/.env` (JIRA_SITE/EMAIL/TOKEN — secrets mounted, never baked), plus **corrected `opencode.json`** (`/tmp/aialm-dispatch-<proj>-*.json:/app/opencode.json:ro` generowany przez `correctedOpencodeConfig(JIRA_SITE)` gdzie `jira` MCP wskazuje `JIRA_SITE=ai-alm-oss` — fix dla `paligakrzychu` vs `ai-alm-oss` PAT error) i LLM auth `~/.local/share/opencode/auth.json:/home/node/.local/share/opencode/auth.json:ro` (github-copilot) + opcjonalnie `~/.config/opencode/auth.json`. `TOOLSETS` w corrected config: `jira_issues,jira_comments,jira_fields,jira_transitions` ( `transition_issue` jest w `jira_transitions` — bez tego start/koniec nie miałby MCP; `jira_service_desk` wykluczone — powodowało `Personal Access Tokens are not supported`). Zakończenie: `<image> npx opencode run [--model <OPENCODE_MODEL>] <skill> <key>`. Extra args / nameSuffix jako test seam.
- **Detached + logi (wymaganie: widzieć logi).** Dispatcher po każdym `docker run -d` wypisuje `container id/name` + `docker logs` handle (`docker logs <id>`, `-f`, `--logs=<key|id>`). `scripts/dispatcher.mts` po dispatchu robi `docker logs --tail 30` per kontener (best-effort, skill może jeszcze nic nie wypisać). `--status` robi `docker ps -a --filter label=aialm.dispatch` (+ opcjonalnie `aialm.project`) → `docker inspect` → `parseInspectJson` (id 12-chars, name, key z label, State.Status/ExitCode/Health.Status) + `docker logs --tail 20` per kontener.
- **Watch (`--status --watch`).** One-shot, bez demona: filtr running kontenerów → dla każdego `spawn('docker', ['logs','-f','--tail','50', id], {stdio:'inherit'})` równolegle; na SIGINT kill + resolve. Po zakończeniu komunikat `Re-run --status`. Zachowuje no-daemon kontrakt (nie jest żyjącym pollerem).
- **CLI (`scripts/dispatcher.mts`).** Flags: `--project=KEY` (dla dispatch wymagane), `--dry` (tylko wypisz), `--limit=N` (scan cap), `--status` (listing), `--watch` (przy status streaming), `--logs=<id|key>` (resolve key → `docker ps -a --filter label=aialm.dispatch=<key>` → logs), `--image=REF`, `--tail=N`. Env via `loadDotEnv` (jak `orchestrate-ticket.mts`), `ensureSelfAwareFields` + `scanPickupTickets` + `buildDockerRunSpec` + `sh('docker', args)` (`spawnSync`). Assignee gate zostaje w skillu w kontenerze (dispatcher go nie sprawdza — nie mutuje Jiry).
- **Dockerfile (`runtime`).** Lean image `node:22-bookworm-slim` + `uv/uvx` + `opencode-ai@1.18.20` + `git/openssh/tini/procps`, `npm ci` (. + .opencode), build gates `tsc --noEmit` + `vitest run`, `USER node` + `mkdir -p /home/node/.local/share/opencode /home/node/.config/opencode` (dla LLM auth mountu), pre-cache `uvx mcp-atlassian --help` (eliminuje 30s cold-start), `ENV HOME/NODE_OPTIONS`, `ENTRYPOINT tini`, fallback `HEALTHCHECK` via `/proc` (dispatcher nadpisuje `run --health-cmd`).
- **`po-analyze` transitions (AGENTS.md exclusive mutator).** Skill na starcie `AWAITING_AGENT_PICKUP->IN_PROGRESS_BY_AGENT` (`AIALM STAGE/ROLE=PO/AGENT=po-analyze`) + native `AWAITS AGENT PICKUP->AGENT WORKING`, na końcu `IN_PROGRESS->AWAITING_HUMAN_APPROVAL/PO/none` + `AGENT WORKING->AWAITS HUMAN APPROVAL` (idempotent re-run zachowuje chain — nie zostawia `IN_PROGRESS`). Field resolution: duplikaty `AIALM ROLE/STAGE/AGENT` (`customfield_10100..10104` itp.) — **nie** `jira_jira_search_fields` first-hit (dawało `10100` zamiast projektowego `10103` dla WELLBEINGT), tylko `jira_jira_get_issue fields=*all use_display_names` i wybór tego `customfield_*` który faktycznie zawiera wartość na issue (dla WELLBEINGT: `10102/10103/10104`). Assignee gate zrelaksowany na `myself` (`ksw2zdz4h8@privaterelay.appleid.com` dla ai-alm-oss), nie tylko `aialmoss@icloud.com`.
- **Live chyłki:** host `opencode.json` ma `jira=paligakrzychu`, `jira-oss=ai-alm-oss` — bez corrected config `jira_jira_*` dla WELLBEINGT (ai-alm-oss) padał na PAT `third-party user token`; LLM model w kontenerze wymaga mountu `auth.json` (inaczej `UnknownError`/`EACCES mkdir repos`); `mcp-atlassian 0.23.1` `transition_issue` jest w `jira_transitions` toolsecie — pominięcie go blokuje mutacje stanu.
